# moeum의 생활비와 자산 추이 설계 초안

moeum은 Sure 포크에서 매일 확인할 생활비와 결제 의무를 보여주고, 사용자가 선택한 생활비에 따른 자산 추이를 비교합니다. 목표 금액이나 목표일을 정해 행동을 권고하지 않습니다.

상태는 요구사항·목업 확인 완료, 계산 상세 설계 미완료입니다. 이 문서는 검토용 초안이며 구현 승인이 아닙니다. 사용자 개인정보와 실제 재무 수치는 포함하지 않습니다.

2026-11-11 12:26 (Asia/Seoul)에 사용자의 `현재까지 내용을 문서화하고 대기` 요청으로 작업을 중단합니다. 추가 질문·상세 설계·구현·Git 제출은 진행하지 않습니다. 재개 지점은 아래 `대기 상태와 재개 지점` 절입니다.

## 사용자가 자신의 판단에 필요한 정보를 읽습니다

사용자는 하루 한 번 화면을 보고 생활비와 기록 상태를 확인합니다. 더 자세한 분석은 별도 화면으로 접근합니다. 프로그램은 차분하고 정확한 정보를 제공하며, 사용자 대신 투자·절약 행동의 적절성을 평가하지 않습니다.

- 첫 화면은 사용 가능한 생활비, 카드 결제 부담, 입력 확인 상태에 집중합니다.
- 순자산과 기존 Sure 분석 카드는 별도 `자산·흐름` 탭으로 접근합니다. 탭 구성은 목업에서 확인한 안입니다.
- 실제 기록과 미래 예상치를 구분합니다. 예상치의 가정과 기준 시점을 표시합니다.
- 응원 문구, 성과 등급, 목표 달성률, 목표일까지 부족한 금액, 예상 목표 도달일은 표시하지 않습니다.
- 생활비 변경이 자산 추이에 미치는 영향을 보여주되 권장 투자나 상환 전략을 새로 만들지 않습니다.

## Sure 포크에 필요한 정보만 추가합니다

독자 앱 개발 대신 Sure 포크를 사용하는 방향을 선택했습니다. 기존 계좌·거래·분석 기능을 최대한 재사용합니다. 기존 기능을 버리고 재구현할 범위는 확정하지 않았습니다.

| 검토한 방식 | 판단 |
| --- | --- |
| 독자 앱 개발 지속 | Sure 포크 활용으로 대체했습니다. |
| 포크 내부 plugin/mod 격리 | 개발 난도를 낮추기 위한 후보였으며 필수가 아닙니다. 코드 품질에 불리하면 채택하지 않습니다. |
| 기존 Sure 화면 확장 | 중복 순자산 카드 대신 기존 카드와 분석 영역을 활용하는 방향을 선택했습니다. |

스타일은 Sure의 디자인 시스템과 기존 UI를 따릅니다. 컨트롤러·가족 권한·통화 처리·컴포넌트 규칙은 [프로젝트 지침](../AGENTS.md)과 [아키텍처](llm-guides/architecture.md)를 원본으로 합니다. 새로운 의존성이나 별도 앱 구조는 이 설계로 승인하지 않습니다.

확인한 재사용 지점은 다음과 같습니다.

| 원본 | 현재 확인한 역할 |
| --- | --- |

일·주·월 조회와 순자산 변화의 원인 분석이 기존 기능으로 어디까지 가능한지는 추가 조사 대상입니다. 현금흐름 집계와 순자산 증감이 같은 수치라고 가정하지 않습니다.

## 매일 확인 화면에서 생활비와 결제 부담을 봅니다

월 생활비는 사용자가 생각하는 적정 금액을 입력합니다. 목표에서 생활비를 역산하던 초기 제안은 폐기했습니다. 입력한 생활비에 고정 생활비가 포함돼 있다면 같은 고정비를 별도로 다시 차감하지 않습니다.

생활비의 한 기간은 급여일부터 다음 급여일 전날까지입니다. 달력 월별 통계와 기간이 다를 수 있음을 표시합니다. 휴일 등에 따른 실제 입금일 변경과 급여일 변경 시 기간을 처리하는 방식은 상세 설계에서 정합니다.

목업에서 확인한 표시는 설정한 월 생활비, 사용 가능한 생활비, 이미 납부한 생활비, 납부 예정 카드 일시불·할부, 다음 급여 기간의 카드 부담, 할부별 일정입니다. 카드 일시불과 할부는 납부할 급여 기간에서 차감합니다. 생활비에 포함할 거래 분류와 카드 청구 정보의 연결 방식은 아직 확정하지 않았습니다. 남아 있는 목업의 달력 월 문구는 급여 주기에 맞춰 보완해야 합니다.

사용 가능한 생활비와 계좌 잔액, 카드 이용 한도를 구분합니다. 계좌에 돈이 남았다는 이유로 이미 확정된 결제 의무를 무시하지 않습니다.

### 카드 사용과 납부를 중복 차감하지 않습니다

카드 일시불은 납부할 급여 기간의 생활비에서 차감합니다. 다음 기간에 납부할 구매는 현재 생활비를 줄이지 않고 다음 기간의 확정 부담에 즉시 반영합니다. 이후 납부 시 다시 차감하지 않습니다. 사용자는 이번 카드 사용으로 향후 생활비가 줄어드는 효과를 몇 개 기간의 그래프로 확인하기를 원합니다.

무이자 60만 원을 6개월 할부로 구매한 가상 사례에서는 매월 청구되는 10만 원을 해당 월 생활비에서 차감합니다. 첫 청구가 다음 달이면 다음 달부터 반영합니다.

향후 생활비 그래프에는 현재 확정 내역을 기준점으로 함께 표시합니다. 추가 결제 가정은 별도로 비교하며, 기존 할부는 건별로 식별합니다. 새 할부와 기존 각 할부, 일시불, 쓸 수 있는 생활비를 구분합니다. 그래프의 가정 추가만으로 실제 카드 부담이나 설정을 바꾸지 않습니다.

- 순자산에는 구매 시점의 미결제 채무 전체를 반영합니다.
- 카드대금 납부는 현금과 해당 채무의 감소로 연결합니다. 구매와 납부를 두 번 지출로 계산하지 않습니다.
- 이번 회차 청구액과 남은 회차의 원금 전체를 구분합니다. 상세 금액을 다시 추가 차감하지 않습니다.
- 다음 급여 기간의 확정 부담도 표시합니다. 이후 사용으로 늘어날 수 있다는 점을 함께 알립니다.
- 청구액과 미청구 사용액, 취소·환불·조기상환, 수수료 처리의 정확한 집계 계약은 상세 설계에서 확정합니다. 수수료가 미확정이면 무이자로 간주하지 않고 아래 계산 보류 규칙을 적용합니다.

상환액·수수료처럼 계산에 필요한 입력값이 확정되지 않았으면 영향을 받는 지점부터 계산을 보류합니다. 사용자가 임의의 추정값을 넣어 계산을 계속하는 안은 채택하지 않았습니다. 미확정 값을 0원으로 처리하거나 정상·현금 부족 상태로 판정하지 않습니다. 계산 보류의 원인이 된 누락 항목과 기준 시점을 표시합니다. 확정된 거래 기록은 유지하며 영향받지 않는 과거 실적까지 숨기지 않습니다. 급여·고정 생활비를 현재 금액으로 유지하는 명시적 예측 가정은 이 미확정 입력 처리와 구분합니다.

### 거래 없는 날을 사용자가 확인합니다

각 카드에는 마지막 거래 입력 시점을 표시합니다. 입력되지 않은 거래가 없는지와 실제 무거래일을 거래 유무만으로 단정하지 않습니다.

사용자는 간단한 버튼으로 해당 날짜에 거래가 없었음을 확인합니다. 무거래 확인일과 마지막 거래 입력일을 구분하고, 오늘 확인이 과거 미확인일까지 해소하지 않도록 합니다.

거래가 있는 날에도 사용자가 `오늘 기록 확인 완료`를 눌러야 완료로 처리합니다. 거래를 한 건 등록한 사실만으로 일별 기록을 자동 완료하지 않습니다. 마지막 거래 입력 시점과 일별 기록 확인 상태는 서로 다른 정보입니다.

미확인일이 있으면 기록의 기준과 미확인 날짜를 안내합니다. 무지출을 실패로 평가하거나 자산 성과 경고와 혼합하지 않습니다. 확인의 저장 범위와 일별 완결 기준은 상세 설계 미정입니다.

## 생활비를 바꾸면 미래 자산 곡선을 비교합니다

사용자는 생활비 카드에서 `생활비별 자산 추이 비교`를 펼칩니다. 희망 월 생활비를 입력하거나 조정하면, 같은 기간에 그 금액을 매달 유지하는 예상 곡선이 바뀝니다.

비교 기준의 생활비와 입력한 생활비의 순자산 곡선을 같은 축에 표시합니다. 목표 금액·목표일·목표 도달 여부는 계산하거나 표시하지 않습니다. 비교 기간은 목표 기한이 아닙니다.

목업의 12개월 조회 범위와 입력 상한은 임시값입니다. 조회 범위의 기본값·최대값은 아직 제품 결정이 아닙니다. 목업에서 확인한 `원` 단위 직접 입력과 슬라이더는 같은 값을 조작합니다.

시뮬레이션은 비교만 제공하며 실제 설정을 변경하는 적용 버튼을 두지 않습니다. 기준으로 되돌릴 수 있으며, 빈 입력에는 잘못된 예상치를 표시하지 않습니다. 실제 월 생활비는 별도 설정 UI에서 변경합니다. 저장 시 현재 급여 기간부터 반영하고, 이미 쓴 금액과 확정 결제 의무는 유지해 남은 생활비를 다시 계산합니다. 시뮬레이션 안에서 직접 적용하던 이전 안은 사용자 재검토로 폐기했습니다. 비교 기준을 현재 저장된 생활비로 삼아 설정 저장 후 다시 잡는 방식은 AI 설계안입니다.

사용자는 실현 불가능한 계획이나 재정 상태 악화를 텍스트보다 시각적으로 파악하기를 원합니다. 순자산과 의무 납입 후 가용 현금을 분리하고, 사용자가 정한 비상금 기준 미달은 주황 구간으로, 납입 재원 부족은 빨간 구간과 발생 지점으로 표시합니다. 색상과 함께 기준선·마커·짧은 설명을 사용합니다. 납입 재원 부족 시점에서 해당 시나리오의 예상 곡선을 중단하고, 그 이후의 예상 금액은 산출하지 않습니다. 이 표현과 중단 방식은 v10 목업에서 사용자 확인을 받았습니다. 비상금 기준 미달만으로는 곡선을 중단하지 않습니다.

### 기존 상환·비상금 원칙을 유지해 금액과 일정을 재계산합니다

사용자가 가진 상환 순서와 비상금 적립 원칙을 유지합니다. 생활비가 바뀌면 추가상환 여력, 완납 시점, 이후 이자와 자산 추이를 재계산합니다. 상환 순서나 투자 전략 자체를 자동 최적화하지 않습니다.

미래 급여와 고정 생활비는 현재 입력액이 유지된다고 가정합니다. 알려진 변화만 적용 예정일과 함께 입력해 반영합니다. 매월 별도의 급여·고정비 계획을 작성하는 방식은 채택하지 않았습니다. 대출 원리금과 이자·추가상환은 이 가정과 구분해 해당 일정으로 재계산합니다.

계산은 생활비 차액을 기간에 곱하는 것만으로 끝나지 않습니다. 대출별 의무 납입·이자·만기와 추가상환 조건을 반영해야 합니다. 원금 상환과 자기 계좌 간 비상금 이체를 단순 비용으로 처리하지 않습니다.

실물 자산과 대응 부채를 함께 포함합니다. 반환받을 보증금은 자산, 관련 대출과 개인 간 차용금은 부채입니다. 상환 일정이 없는 차용금을 부채에서 제외하거나 임의의 월 상환 일정을 만들지 않습니다. 묶인 자산을 당장 쓸 수 있는 현금으로 간주하지 않습니다.

정확한 금융 수치는 사용자가 관리하는 비공개 입력에서 읽습니다. 공개 문서·fixtures·스크린샷에는 합성 자료만 사용합니다. 개인별 금융기관과 숫자를 제품 기본값으로 고정하지 않습니다.

## 1차 범위와 후속 설계를 구분합니다

| 구분 | 범위 |

## 실패 모드와 남은 결정을 명시합니다

다음 목록은 미정 사항과 이미 결정한 계산 제약을 함께 정리합니다. 확정 정책을 다시 질문하지 않고, 미정인 상세 계약만 보완합니다.

1. [일부 미정] 급여일 기준 기간과 납부 기간 차감은 확정했습니다. 카드 청구 데이터 연결, 휴일의 급여 조기 입금과 급여일 변경 처리는 미정입니다.
2. 생활비에 포함할 거래·카테고리와 의무 상환을 구분합니다. 카드 구매와 납부를 잇는 기존 Sure 표현을 조사합니다.
3. 미래 급여·고정비는 현재 금액과 예정된 변경을 사용합니다. 이율·상환액을 포함한 입력의 저장 원본, 기준일과 확정·추정 상태를 정합니다.
4. [확정 제약] 만기 상환 재원이 부족하거나 생활비가 의무 납입을 침해하는 최초 시점을 검출합니다. 해당 시나리오는 그 시점까지 표시하고 이후 예상치는 산출하지 않습니다. 미납·추가 차입을 가정해 곡선을 연장하지 않습니다.
5. [확정 제약] 미확정 수수료·상환액·잔액이 필요한 지점부터 계산을 보류합니다. 추정값이나 0원으로 대체하지 않습니다. 잔액 합계가 불일치하는 자료도 묵시적으로 보정하지 않고 확인이 필요한 항목으로 표시합니다.
6. 만기와 날짜·이자 일수·반올림·중도상환 규칙, 비상금 상한 도달 후 배분을 실제 입력과 대조합니다.
7. 입력 완결 확인의 사용자·가족 범위와 과거 기록 수정 시 확인 상태 처리를 정합니다.
8. 구현 담당자와 이후 운영·유지보수 담당자를 확인합니다.

## 결정 변경을 보존합니다

이 세션에서 결정은 다음 순서로 바뀌었습니다. 최신 본문이 유효합니다.

1. 1억 목표 KPI·필요 속도·응원과 경고 중심 제안을 검토했습니다.
2. 속도 판단과 가벼운 목표 표현을 반려하고 중립적 정보 제공으로 바꿨습니다.
3. 순자산 정보를 기존 Sure 카드와 중복하지 않도록 재사용하는 안을 확인했습니다.
4. 매일 보는 첫 화면에서 순자산·목표 정보를 빼고 분석을 별도 탭으로 옮겼습니다.
5. 고정 목표일의 금액 비교와 전략에 따른 도달일 비교를 검토했습니다.
6. 목표 금액·목표일 자체를 제외했습니다. 사용자가 입력한 생활비에 따른 자산 추이를 비교하는 안을 확인했습니다.
7. 급여일 기준 생활비 기간, 일시불·할부의 납부 기간 차감, 거래가 있는 날의 직접 기록 확인을 선택했습니다.
8. 시뮬레이션 직접 적용을 검토한 뒤 폐기했습니다. 별도 설정 UI에서 현재 급여 기간에 반영합니다.
9. 미래 급여·고정 생활비는 현재 금액과 예정된 변화로 계산하고, 상환·비상금 원칙은 유지합니다.
10. 현금 부족 이후의 예상치 중단과, 필수 값 미확정 시 계산 보류를 선택했습니다. 임의 추정값 입력으로 계산을 이어가는 안은 채택하지 않았습니다.
11. 향후 생활비의 기준 그래프와 추가 결제 비교 그래프, 기존·신규 할부의 구분을 확인했습니다.

문서 전체 승인은 아직 받지 않았습니다. 계산 상세 설계를 보완한 뒤 설계 승인을 받고 구현 계획을 작성합니다.


## 대기 상태와 재개 지점

사용자는 현재까지의 내용을 문서화하고 대기하도록 요청했습니다. 이 요청으로 설계 전체 승인·구현·커밋·푸시·PR 제출 권한을 추가로 해석하지 않습니다. 재개 요청 전에는 추가 질문이나 작업을 진행하지 않습니다.

현재 보존한 산출물은 이 설계 초안, 로컬 최신 목업 v17, 브라우저 검증 스크립트와 증거입니다. 사용자 재무 원본과 대화에서 보완한 개인정보는 로컬 비공개 자료로 별도 보존합니다. 공개 설계·합성 목업에 그 숫자를 옮기지 않습니다.

재개하면 다음 순서로 이어갑니다.

1. 이 문서의 확정 결정과 최신 파일 상태를 대조합니다. 폐기한 목표 중심 계산과 시뮬레이션 적용 버튼을 되살리지 않습니다.
2. 기존 Sure 데이터 모델에서 카드·할부·상환 정보를 어떻게 연결할지 조사합니다. 생활비 거래 분류, 일별 확인 범위·수정 처리, 날짜·이자·반올림, 비상금 상한 이후 배분 등의 미정 계약을 좁힙니다.
3. 실제 금융 수치는 비공개 입력에서 확인하고, 공개 설계와 시험은 합성 사례로 작성합니다. 입력 원본의 누락·불일치를 확정값처럼 사용하지 않습니다.
4. 계산 상세 설계와 실제 수용 기준을 마무리하고 설계 문서의 승인을 받습니다. 이후 구현 계획을 작성합니다. 목업 확인을 실제 금융 계산 검증이나 전체 설계 승인으로 확대하지 않습니다.

# moeum의 생활비와 자산 추이 설계 초안

moeum은 Sure 포크에서 매일 확인할 생활비와 결제 의무를 보여주고, 사용자가 선택한 생활비에 따른 자산 추이를 비교합니다. 목표 금액이나 목표일을 정해 행동을 권고하지 않습니다.

상태는 요구사항·목업 확인 완료, 계산 상세 설계 미완료입니다. 이 문서는 검토용 초안이며 구현 승인이 아닙니다. 사용자 개인정보와 실제 재무 수치는 포함하지 않습니다.

2026-11-11 12:26 (Asia/Seoul)에 사용자의 `현재까지 내용을 문서화하고 대기` 요청으로 중단했고, 2026-11-12 사용자가 생활비·카드·할부 데이터 연결 조사와 계산 상세 설계 재개를 선택했습니다. 현재는 상세 설계를 진행하며 제품 구현은 승인되지 않았습니다.

## 사용자가 자신의 판단에 필요한 정보를 읽습니다

사용자는 하루 한 번 화면을 보고 생활비와 기록 상태를 확인합니다. 더 자세한 분석은 별도 화면으로 접근합니다. 프로그램은 차분하고 정확한 정보를 제공하며, 사용자 대신 투자·절약 행동의 적절성을 평가하지 않습니다.

- 첫 화면은 사용 가능한 생활비, 카드 결제 부담, 입력 확인 상태에 집중합니다.
- 순자산과 기존 Sure 분석 카드는 별도 `자산·흐름` 탭으로 접근합니다. 탭 구성은 목업에서 확인한 안입니다.
- 실제 기록과 미래 예상치를 구분합니다. 예상치의 가정과 기준 시점을 표시합니다.
- 응원 문구, 성과 등급, 목표 달성률, 목표일까지 부족한 금액, 예상 목표 도달일은 표시하지 않습니다.
- 생활비 변경이 자산 추이에 미치는 영향을 보여주되 권장 투자나 상환 전략을 새로 만들지 않습니다.

## Sure 포크에 필요한 정보만 추가합니다

독자 앱 개발 대신 Sure 포크를 사용하는 방향을 선택했습니다. 기존 계좌·거래·분석 기능을 최대한 재사용합니다. 기존 기능을 버리고 재구현할 범위는 확정하지 않았습니다.

| 검토한 방식 | 판단 |
| --- | --- |
| 독자 앱 개발 지속 | Sure 포크 활용으로 대체했습니다. |
| 포크 내부 plugin/mod 격리 | 개발 난도를 낮추기 위한 후보였으며 필수가 아닙니다. 코드 품질에 불리하면 채택하지 않습니다. |
| 기존 Sure 화면 확장 | 중복 순자산 카드 대신 기존 카드와 분석 영역을 활용하는 방향을 선택했습니다. |

스타일은 Sure의 디자인 시스템과 기존 UI를 따릅니다. 컨트롤러·가족 권한·통화 처리·컴포넌트 규칙은 [프로젝트 지침](../AGENTS.md)과 [아키텍처](llm-guides/architecture.md)를 원본으로 합니다. 새로운 의존성이나 별도 앱 구조는 이 설계로 승인하지 않습니다.

확인한 재사용 지점은 다음과 같습니다.

### 기존 Sure 분석과 moeum 생활비의 기준을 구분합니다

기존 Sure의 거래 원장과 구매일 기준 예산·소비 분석을 유지합니다. moeum 생활비에는 카드 납부가 배정된 급여 기간 기준의 계산을 추가합니다. 두 화면에 계산 기준을 표시하며, 거래 원장의 구매일을 납부일로 바꾸지 않습니다.

합성 사례로 11월 20일 구매한 12만 원을 12월 10일 납부한다면, 기존 소비 분석은 11월 20일이 속한 기간에 반영하고 moeum 생활비는 12월 10일이 속한 급여 기간에 반영합니다. 순자산은 구매 시 생긴 채무와 납부 시 현금·채무 감소를 별도로 반영합니다.

2026-11-12 코드 조사에서 확인한 재사용 범위는 다음과 같습니다. 아래 한계는 구현 사실이며, 새 저장 모델을 승인한 것은 아닙니다.

| 원본 | 확인한 기능 | moeum 연결에 필요한 사항 |
| --- | --- | --- |
| [`CreditCard`](../app/models/credit_card.rb) | 마감일·납부일과 거래 기반 청구 요약 | 구매별 청구회차 배정, 예상·확정 구분 |
| [`Transaction`](../app/models/transaction.rb)·[`Transfer`](../app/models/transfer.rb) | 카드대금 납부를 구매와 구분하고 예산 중복 집계 제외 | 생활비 대상 거래와 납부 급여 기간 연결 |
| [`Budget.period_for`](../app/models/budget.rb) | 고정 월 시작일 기준 기간 | 실제 급여 입금으로 변하는 기간 경계·이력 |
| [`RecurringTransaction`](../app/models/recurring_transaction.rb)·[`RecurringOccurrence`](../app/models/recurring_occurrence.rb) | 할부 유형, 유한 회차, 회차별 납부 예정일·상태 | 원구매 전체 채무와 카드 청구회차·원금·수수료 연결 |
| [`RecurringAllocation`](../app/models/recurring_allocation.rb) | 회차와 실제 거래·수동 납부 금액 배분 | 납부 후에도 해당 급여 기간의 소비 부담 보존 |

기존 `Budget.actual_spending`은 거래일 기준 집계를 사용하므로 moeum 생활비 계산으로 그대로 대체할 수 없습니다. 카드 `statement_summary.remaining`만 차감하면 납부 후 남은 생활비가 되살아나는 문제가 생깁니다. 납부 여부와 무관하게 해당 기간에 배정된 부담을 보존해야 합니다. 기존 `month_start_day`는 1~28일 고정 설정이므로 실제 입금 기반 기간을 그대로 표현하지 못합니다.

## 매일 확인 화면에서 생활비와 결제 부담을 봅니다

월 생활비는 사용자가 생각하는 적정 금액을 입력합니다. 목표에서 생활비를 역산하던 초기 제안은 폐기했습니다. 입력한 생활비에 고정 생활비가 포함돼 있다면 같은 고정비를 별도로 다시 차감하지 않습니다.

생활비의 한 기간은 실제 급여 입금 확인일부터 다음 실제 급여 입금 확인일 전날까지입니다. 휴일 때문에 정기 급여일인 25일보다 이른 23일에 입금되면 23일부터 새 기간을 시작합니다. 1회 급여 기간마다 설정한 생활비를 그대로 배정하며, 기간이 길거나 짧아져도 일수 비례로 늘리거나 줄이지 않습니다. 달력 월별 통계와 기간이 다를 수 있음을 표시합니다. 미래 입금일이 미확정인 기간은 정기 급여일을 기준으로 예정 기간을 표시합니다. 실제 입금을 확인하면 기간과 카드 부담을 재계산합니다. 급여일 변경 이력 처리는 상세 설계에서 정합니다.

목업에서 확인한 표시는 설정한 월 생활비, 사용 가능한 생활비, 이미 납부한 생활비, 납부 예정 카드 일시불·할부, 다음 급여 기간의 카드 부담, 할부별 일정입니다. 카드 일시불과 할부는 납부할 급여 기간에서 차감합니다. 생활비에는 일반 소비를 기본 포함하고, 별도로 계산하는 고정비·상환·투자·이체는 제외합니다. 설정 생활비에 포함된 고정비를 별도 고정비로도 차감하지 않습니다. 거래별 포함·제외 분류와 카드 청구 정보의 구체적인 연결 방식은 상세 설계에서 정합니다. 남아 있는 목업의 달력 월 문구는 급여 주기에 맞춰 보완해야 합니다.

사용 가능한 생활비와 계좌 잔액, 카드 이용 한도를 구분합니다. 계좌에 돈이 남았다는 이유로 이미 확정된 결제 의무를 무시하지 않습니다.

### 카드 청구 예정과 확정을 구분합니다

1차 버전은 거래를 기준으로 카드 청구 일정을 자동 산출하고 예상으로 표시합니다. 카드사 청구 내역을 확인하면 확정으로 전환합니다. 자동 산출만으로 카드사가 확정한 일정이나 금액이라고 표시하지 않습니다. 예상 일정과 실제 청구가 다를 때의 조정, 청구 확인 입력과 원거래 연결은 상세 설계 미정입니다. 미확정 수수료를 0원으로 대체하지 않는 계산 보류 원칙은 유지합니다.

자동 산출한 예상 청구도 배정된 급여 기간의 사용 가능한 생활비에서 미리 차감합니다. 결과에 예상 포함 여부를 표시하고 확정 부담과 예상 부담을 구분합니다. 청구가 확정될 때 예상 부담에 확정 부담을 추가로 더하지 않고 같은 부담을 대체해야 합니다. 필수 수수료 등 입력이 빠졌으면 영향을 받는 계산을 보류하며 확정 숫자로 표시하지 않습니다.

처음 사용할 때 이미 진행 중인 할부는 확인한 잔여 회차·금액·납부 일정으로 등록할 수 있습니다. 과거 원구매부터 전체 납부 이력을 복원하도록 요구하지 않습니다. 잔여 원금이 기존 카드 부채에 이미 포함돼 있다면 일정을 등록했다는 이유로 채무를 다시 추가하지 않습니다. 부채 잔액과 남은 원금의 연결·대사 계약은 상세 설계에서 보완합니다.

취소·환불은 카드사의 실제 반영 일정에 따라 청구액이 줄어드는 급여 기간의 부담을 감소시킵니다. 이미 납부한 원구매가 과거 급여 기간에 속하더라도 원래 기간의 생활비를 소급 복원하지 않습니다. 환불 반영 회차가 미확정이면 확정된 감소로 간주하지 않습니다. 일반 소비 이외 항목의 환불을 생활비로 편입하지 않도록 원구매의 포함·제외 분류를 함께 보존해야 합니다.

### 카드 사용과 납부를 중복 차감하지 않습니다

카드 일시불은 납부할 급여 기간의 생활비에서 차감합니다. 다음 기간에 납부할 구매는 현재 생활비를 줄이지 않고 다음 기간의 예상 부담에 즉시 반영합니다. 카드사 청구 확인 후 같은 부담을 확정으로 대체하며, 이후 납부 시 다시 차감하지 않습니다. 사용자는 이번 카드 사용으로 향후 생활비가 줄어드는 효과를 몇 개 기간의 그래프로 확인하기를 원합니다.

무이자 60만 원을 6개월 할부로 구매한 가상 사례에서는 매월 청구되는 10만 원을 해당 월 생활비에서 차감합니다. 첫 청구가 다음 달이면 다음 달부터 반영합니다.

향후 생활비 그래프에는 현재 등록된 구매·할부의 확정·예상 부담을 기준점으로 함께 표시합니다. 추가 결제 가정은 별도로 비교하며, 기존 할부는 건별로 식별합니다. 새 할부와 기존 각 할부, 일시불, 쓸 수 있는 생활비를 구분합니다. 그래프의 가정 추가만으로 실제 카드 부담이나 설정을 바꾸지 않습니다.

- 순자산에는 구매 시점의 미결제 채무 전체를 반영합니다.
- 카드대금 납부는 현금과 해당 채무의 감소로 연결합니다. 구매와 납부를 두 번 지출로 계산하지 않습니다.
- 이번 회차 청구액과 남은 회차의 원금 전체를 구분합니다. 상세 금액을 다시 추가 차감하지 않습니다.
- 다음 급여 기간의 확정 부담도 표시합니다. 이후 사용으로 늘어날 수 있다는 점을 함께 알립니다.
- 청구액과 미청구 사용액, 취소·환불·조기상환, 수수료 처리의 정확한 집계 계약은 상세 설계에서 확정합니다. 수수료가 미확정이면 무이자로 간주하지 않고 아래 계산 보류 규칙을 적용합니다.

상환액·수수료처럼 계산에 필요한 입력값이 확정되지 않았으면 영향을 받는 지점부터 계산을 보류합니다. 사용자가 임의의 추정값을 넣어 계산을 계속하는 안은 채택하지 않았습니다. 미확정 값을 0원으로 처리하거나 정상·현금 부족 상태로 판정하지 않습니다. 계산 보류의 원인이 된 누락 항목과 기준 시점을 표시합니다. 확정된 거래 기록은 유지하며 영향받지 않는 과거 실적까지 숨기지 않습니다. 급여·고정 생활비를 현재 금액으로 유지하는 명시적 예측 가정은 이 미확정 입력 처리와 구분합니다.

### 거래 없는 날을 사용자가 확인합니다

각 카드에는 마지막 거래 입력 시점을 표시합니다. 입력되지 않은 거래가 없는지와 실제 무거래일을 거래 유무만으로 단정하지 않습니다.

사용자는 간단한 버튼으로 해당 날짜에 거래가 없었음을 확인합니다. 무거래 확인일과 마지막 거래 입력일을 구분하고, 오늘 확인이 과거 미확인일까지 해소하지 않도록 합니다.

거래가 있는 날에도 사용자가 `오늘 기록 확인 완료`를 눌러야 완료로 처리합니다. 거래를 한 건 등록한 사실만으로 일별 기록을 자동 완료하지 않습니다. 마지막 거래 입력 시점과 일별 기록 확인 상태는 서로 다른 정보입니다.

일별 기록 확인은 날짜마다 한 번 수행하며 해당 날짜의 생활비 대상 기록 전체를 확인했다는 뜻입니다. 카드·계좌마다 별도로 완료 버튼을 누르도록 요구하지 않습니다. 카드별 마지막 입력 시점은 일별 확인과 별도로 유지합니다.

생활비 설정과 일별 확인 상태는 사용자별로 관리합니다. 1차는 본인 소유이며 접근 권한이 있는 카드·계좌의 생활비 대상 기록만 계산·확인 범위에 포함합니다. 공유 계좌는 제외하고 기존 가족·계좌 권한을 확대하지 않습니다. 소유자가 미지정인 계좌를 임의로 본인 계좌로 간주하지 않습니다. 확인 후 해당 날짜의 거래를 추가·수정·삭제해도 완료 상태는 유지하고 `확인 후 변경됨`을 함께 표시합니다. 변경된 기록은 생활비 계산에는 반영하며, 확인 상태 유지가 이전 금액을 고정한다는 뜻은 아닙니다.

미확인일이 있으면 기록의 기준과 미확인 날짜를 안내합니다. 무지출을 실패로 평가하거나 자산 성과 경고와 혼합하지 않습니다. 완료와 확인 이후 변경 유무를 구분하며 최신 기록을 다시 확인했다고 자동 간주하지 않습니다.

## 생활비 연결 계산 초안과 수용 사례

아래 데이터 연결과 계산 절차는 확정된 사용자 결정을 구현 가능한 계약으로 옮긴 AI 제안입니다. 새 테이블·마이그레이션·화면 구현은 승인되지 않았습니다. 이번 상세화 범위는 생활비·카드·할부 연결이며, 대출 이자·추가상환·비상금 배분을 포함한 전체 자산 예측 설계는 별도 미완료입니다.

### 원장과 생활비 계산을 분리합니다

검토한 방식은 기존 예산 집계까지 납부 기간 기준으로 바꾸는 방식과, 기존 집계를 유지하고 생활비 계산을 추가하는 방식입니다. 사용자는 후자를 선택했습니다. 기존 분석의 의미를 보존하고 원장·거래·반복 일정을 재사용합니다. 원장과 별도로 소비 거래를 중복 생성하는 방식은 채택하지 않습니다.

| 필요한 정보 | 연결 제안 |
| --- | --- |
| 사용자 생활비 설정 | 사용자·통화·기간별 설정액·적용 시점. 본인 소유·접근 가능 계좌만 포함하고 공유 계좌 제외. 가족 소속과 계좌 접근 권한은 기존 경계 유지 |
| 급여 기간 | 실제 급여 입금 근거·확정 시작일, 미래 정기 급여일과 예정 여부. 실제 입금 확인 시 경계와 부담 배정 재계산 |
| 생활비 대상 소비 | 기존 거래 식별자와 포함·제외 근거. 원거래 날짜는 유지 |
| 카드 회차별 부담 | 원거래 또는 초기 잔여 일정, 카드, 회차, 납부일, 원금·수수료, 통화, 예상·확정 상태, 귀속 급여 기간 |
| 청구 확인·납부·환불 | 같은 부담을 식별할 연결과 카드사 반영일. 납부는 부담을 재생성하지 않고, 환불은 반영 기간의 부담 조정 |
| 일별 확인 | 사용자·날짜·확인 시각과 이후 변경 판별 근거. 완료 상태와 변경 표시는 별도 관리 |

예상·확정 청구와 원장 거래를 연결할 식별자는 유지해야 합니다. 같은 거래의 재입력·재계산·반복 실행이 별도의 부담을 추가하면 안 됩니다. 구체 모델명과 저장 구조는 상세 계약 확정 뒤 구현 계획에서 정합니다.

### 급여 기간에 배정된 부담을 한 번만 차감합니다

1. 본인 소유이며 접근 권한이 있는 카드·계좌의 생활비 포함 거래를 선정합니다. 공유 계좌는 제외합니다. 별도 고정비·상환·투자·이체와 카드대금 납부 자체는 소비 차감에서 제외합니다.
2. 실제 급여 입금으로 확정 기간을 구성하고 미래는 정기 급여일 기준 예정 기간으로 구성합니다. 기간 시작일은 포함하고 다음 시작일은 다음 기간에 포함합니다.
3. 현금·체크카드 등 카드 청구를 거치지 않는 소비는 거래가 발생한 급여 기간에 배정하는 안을 제안합니다. 카드 소비는 회차별 납부일이 속한 급여 기간에 배정합니다.
4. 기간에 배정된 카드 부담은 이미 납부했는지와 관계없이 생활비 사용액으로 유지합니다. 확정 청구는 기존 예상 부담을 대체하며 새 부담으로 더하지 않습니다.
5. 환불은 원래 소비 기간이 아니라 카드사가 부담을 줄인 기간의 조정으로 연결합니다. 이미 적용한 환불을 다시 차감하지 않습니다.
6. 설정 생활비에서 대상 소비와 해당 기간 카드 부담을 빼고 환불 조정을 반영합니다. 원금·수수료 등 필수 값이 빠졌거나 연결이 불일치하면 영향을 받는 계산을 보류하고 누락 항목을 표시합니다.

계산에서 `설정액 - 비카드 생활비 소비 - 카드 부담 + 해당 기간 환불 조정`을 사용한다면, 카드 부담은 환불 전 금액이어야 합니다. 카드사 확정 청구액에 환불이 이미 반영돼 있다면 별도 환불 조정을 다시 더하지 않습니다. 순자산은 기존 원장의 자산·채무 변화를 사용하며 이 생활비 합계를 순자산에서 다시 차감하지 않습니다.

## 생활비를 바꾸면 미래 자산 곡선을 비교합니다

사용자는 생활비 카드에서 `생활비별 자산 추이 비교`를 펼칩니다. 희망 월 생활비를 입력하거나 조정하면, 같은 기간에 그 금액을 매달 유지하는 예상 곡선이 바뀝니다.

비교 기준의 생활비와 입력한 생활비의 순자산 곡선을 같은 축에 표시합니다. 목표 금액·목표일·목표 도달 여부는 계산하거나 표시하지 않습니다. 비교 기간은 목표 기한이 아닙니다.

목업의 12개월 조회 범위와 입력 상한은 임시값입니다. 조회 범위의 기본값·최대값은 아직 제품 결정이 아닙니다. 목업에서 확인한 `원` 단위 직접 입력과 슬라이더는 같은 값을 조작합니다.

시뮬레이션은 비교만 제공하며 실제 설정을 변경하는 적용 버튼을 두지 않습니다. 기준으로 되돌릴 수 있으며, 빈 입력에는 잘못된 예상치를 표시하지 않습니다. 실제 월 생활비는 별도 설정 UI에서 변경합니다. 저장 시 현재 급여 기간부터 반영하고, 이미 쓴 금액과 확정 결제 의무는 유지해 남은 생활비를 다시 계산합니다. 시뮬레이션 안에서 직접 적용하던 이전 안은 사용자 재검토로 폐기했습니다. 비교 기준을 현재 저장된 생활비로 삼아 설정 저장 후 다시 잡는 방식은 AI 설계안입니다.

사용자는 실현 불가능한 계획이나 재정 상태 악화를 텍스트보다 시각적으로 파악하기를 원합니다. 순자산과 의무 납입 후 가용 현금을 분리하고, 사용자가 정한 비상금 기준 미달은 주황 구간으로, 납입 재원 부족은 빨간 구간과 발생 지점으로 표시합니다. 색상과 함께 기준선·마커·짧은 설명을 사용합니다. 납입 재원 부족 시점에서 해당 시나리오의 예상 곡선을 중단하고, 그 이후의 예상 금액은 산출하지 않습니다. 이 표현과 중단 방식은 v10 목업에서 사용자 확인을 받았습니다. 비상금 기준 미달만으로는 곡선을 중단하지 않습니다.

### 기존 상환·비상금 원칙을 유지해 금액과 일정을 재계산합니다

사용자가 가진 상환 순서와 비상금 적립 원칙을 유지합니다. 생활비가 바뀌면 추가상환 여력, 완납 시점, 이후 이자와 자산 추이를 재계산합니다. 상환 순서나 투자 전략 자체를 자동 최적화하지 않습니다.

미래 급여와 고정 생활비는 현재 입력액이 유지된다고 가정합니다. 알려진 변화만 적용 예정일과 함께 입력해 반영합니다. 매월 별도의 급여·고정비 계획을 작성하는 방식은 채택하지 않았습니다. 대출 원리금과 이자·추가상환은 이 가정과 구분해 해당 일정으로 재계산합니다.

계산은 생활비 차액을 기간에 곱하는 것만으로 끝나지 않습니다. 대출별 의무 납입·이자·만기와 추가상환 조건을 반영해야 합니다. 원금 상환과 자기 계좌 간 비상금 이체를 단순 비용으로 처리하지 않습니다.
